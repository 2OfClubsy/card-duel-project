# Week 3 Reflection

## Learning points

During Week 3, the team learned how to move from a simple list of user stories to a more structured issue-based Product Backlog.

The main learning points were:

* Product Backlog Items should be clear, traceable, and connected to GitHub Issues.
* User stories need stable IDs so that they can be tracked even when the platform gives them different issue numbers.
* Sprint planning becomes easier when MVP scope, Sprint milestone, priorities, assignees, reviewers, and story points are visible in one place.
* Acceptance criteria make it easier to check whether MVP v1 items are actually complete.
* GitHub Projects can be used not only as a task board, but also as Product Backlog, Sprint Backlog, and MVP scope evidence.
* Pull requests are stronger evidence when they are linked to issues, reviewed by another team member, and connected to acceptance criteria.
* A SemVer release and changelog make the delivered MVP v1 easier to identify and verify.
* Customer review evidence needs to be written clearly, especially when the meeting was offline and not recorded.

The team also learned that documentation work should be treated as part of the product workflow, not as a separate last-minute activity.

## Validated assumptions

Several assumptions were validated during MVP v1 planning, delivery, and customer review.

First, the team confirmed that the project direction should remain focused on a 3D card-duel prototype. This matched the customer feedback from the previous assignment and helped the team keep the MVP v1 scope realistic.

Second, the team validated that MVP v1 should focus on the first playable vertical slice instead of trying to implement the full card-combat system immediately. The selected MVP v1 scope includes starting a game, entering the 3D lobby, looking around, interacting with the card table, and seeing the initial card setup.

Third, the team confirmed that the customer accepted the current Product Backlog, Sprint Backlog, MVP v1 Scope, user stories, and acceptance criteria. The customer stated that the current state was sufficient for the approval mark.

Fourth, the team validated that optional art references could improve the visual direction later, but they were not required for MVP v1 approval.

Finally, the team confirmed that GitHub Issues, GitHub Projects, milestones, labels, reviewed pull requests, release evidence, and screenshots can provide enough public evidence for Assignment 3 when organized properly.

## Friction and gaps

The team found several friction points and gaps during Week 3.

One source of friction was the amount of GitHub workflow setup required. Issue templates, labels, project views, milestone usage, PR templates, changelog workflow, releases, and evidence screenshots all had to be aligned carefully.

Another difficulty was link checking. Some links, especially GitHub Project links and relative links, had to be checked and adjusted so that GitHub Actions and external viewers could access them correctly.

The team also had to manage the difference between customer meeting evidence and transcript evidence. Since the customer review was offline and not recorded, the team used written notes and a summary instead of a transcript.

A remaining product gap is that MVP v1 does not yet include the full card gameplay loop. Advanced card selection, playing a selected card, opponent behavior, round result feedback, audio, and stronger visual style are planned for later versions.

Another gap is that the current MVP v1 is a prototype build, not a complete game. It demonstrates the first playable 3D flow, but the combat mechanics and deeper game design still require future work.

## Planned response

In the next Sprint, the team will continue from the verified MVP v1 scope and move toward a more interactive card-duel experience.

The planned response is:

* Continue refining the Product Backlog and keep `docs/user-stories.md` synchronized with GitHub Issues.
* Use the roadmap to decide which MVP v2 items should be selected next.
* Focus future implementation on card selection, playing a selected card, opponent presence, and round feedback.
* Keep using issue-linked branches and reviewed pull requests for every meaningful change.
* Continue updating `CHANGELOG.md` when user-visible changes are made.
* Add optional art references or visual-direction notes if the team decides they are useful for the next Sprint.
* Keep customer feedback connected to backlog updates so that future scope decisions remain traceable.

The team will use the existing Sprint milestone, MVP labels, roadmap, Definition of Done, and Week 3 evidence structure as the base for the next iteration.
